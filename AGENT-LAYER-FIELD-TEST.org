#+TITLE: Agent layer field test: three Claude Code sessions building a todo app
#+DATE: 2026-09-20

* What was run

Four atty sessions on macOS (Darwin 25.4.0, SBCL 2.6.5, the binary from
~make FOREIGN=1 install PREFIX=$HOME/.local~), driven entirely through
~atty agent~ from a fifth pane. No client was attached to any of them.

| session | command given to ~atty serve~                        | role                        |
|---------+------------------------------------------------------+-----------------------------|
| arch    | ~cd ~/git/testingautomatty && exec claude ...~        | owns SPEC.md, reviews       |
| impl    | ~cd ~/git/testingautomatty && exec claude ...~        | owns todo/                  |
| test    | ~cd ~/git/testingautomatty && exec claude ...~        | owns tests/, pyproject.toml |
| ctl     | ~claude --permission-mode acceptEdits~                | control, bare command       |

All four ran ~claude --permission-mode acceptEdits~, so every Bash call
raised a permission dialog. That was the point: a dialog is the thing the
agent layer exists to notice.

The orchestration loop was the one the README describes. ~atty agent prompt~
to give work, ~atty agent read~ to see the screen, ~atty agent say~ to answer
a dialog, ~atty agent list~ / ~wait~ / ~explain~ to decide when to act.

* Result

The app got built. ~/git/testingautomatty/ holds 1286 lines across
todo/store.py, todo/cli.py, tests/test_store.py, tests/test_cli.py,
pyproject.toml and a SPEC.md carrying nine clarifications the architect
negotiated. Verified independently, not taken from the agents:

: 105 passed in 0.11s

and the CLI behaves to spec end to end, including the three exit codes
(0 success, 1 unknown id, 2 argparse usage error).

The collaboration itself worked, and worked in the interesting direction.
The test agent found a real spec violation (id reuse after removing the
highest id), escalated a spec ambiguity rather than guessing, and the
architect overruled it: both rulings landed on the existing implementation,
so the tests changed and the code did not. Three separate relay rounds ran
through ~atty agent prompt~ with no state lost.

* Findings

Ranked by what they cost an orchestrator.

** 1. A wrapped command is never classified, and an unclassified pane cannot report =blocked=

~claude-code-p~ (src/agent/claude-code.lisp:7) tests the basename of the
*first word* of the command string. But a pane's command is handed to
~/bin/sh -c~ (src/pty/pty.lisp:167), so any shell fragment is legal. The
moment the command is ~cd somewhere && exec claude~, or has an env prefix,
or goes through a wrapper, the first word is not ~claude~ and the pane falls
back to the generic ~agent~ class.

The generic class has no rules at all:

: (defgeneric agent-rules (agent) (:method ((agent agent)) nil))   ; agent.lisp:20

and ~agent-signal~ with no rules can only answer ~:busy~ or ~:quiet~
(agent.lisp:158-167), which publish as =working= and =idle=. *An
unclassified pane can never say =blocked=.* Not "rarely". Never.

Measured, at the end of the run:

: arch:1   idle; the screen says quiet     0 rules
: impl:1   idle; the screen says quiet     0 rules
: test:1   idle; the screen says quiet     0 rules
: ctl:1    idle; the screen says idle     14 rules

The A/B, same program, same dialog, at the same moment:

: test:1  agent        working   <- sitting on "Do you want to proceed?"
: ctl:1   claude-code  blocked   <- sitting on "Do you want to proceed?"

So for the whole run, on all three panes doing the actual work, the headline
feature was inactive. What was left was "has the screen changed lately",
which is what =working= and =idle= degrade to.

Two further effects of the same cause:

- The very first thing Claude Code shows in an untrusted directory is a
  blocking trust dialog. It read as =idle=, "the screen says quiet". Its text
  is "Enter to confirm · Esc to cancel", which the ~live-blocked-form~ rule
  (priority 980) matches exactly, so the rule was right and never got to run.
- Classification is re-derived from the OSC title on every title change
  (~agent-become~, agent.lisp:27). arch:1 was observed as ~claude-code~ at
  22:05 and as ~agent~ later in the same run. The kind flaps, and the rule
  table appears and disappears with it.

Fix shape: decide the kind from the program actually running in the pane
rather than from the string that was spawned. The pane owns the pty, so the
foreground process group is available. Failing that, match any word of the
command, and never let a title change demote a pane that was already
recognised.

** 2. =prompt --until idle= and =wait= return on an idle the paste itself created

Timed deliberately against an idle pane, with a prompt whose work takes
about half a minute:

: state before: ctl:1  claude-code  idle
: prompt --until idle returned after 5s   -> printed "idle", exit 0
: state right after: ctl:1 claude-code idle
: ... pane actually went "working" 16s later

Independently corroborated by a state watcher running in another process,
and seen again unprompted: ~atty agent wait arch:1~ returned =idle= after
24s while arch was still mid-turn.

Cause: pasting the prompt moves the screen, which publishes =working=. The
model has not emitted anything yet, so the screen goes quiet. ~+hold+~ is
700ms (agent.lisp:5), and after 700ms of quiet =idle= is published. The
~--until~ predicate (main.lisp:180-186) accepts the first =idle= it sees and
returns. 700ms is shorter than the gap between a coding agent's tool calls,
so the same misfire happens mid-turn as well.

This is the finding that matters most for scripting, because it fails
*quietly and in the success direction*. The caller gets "idle" and exit 0 and
goes on to read a screen that has not changed yet.

Fix shape: ~:agent-prompt~ should stamp an epoch on the pane, and ~--until~
should ignore anything published before the Return was sent, then require a
=working= -> =idle= transition after it. A quiet threshold alone cannot tell
"finished" from "thinking".

** 3. =agent prompt= into a mis-classified pane is an approval keystroke

~:agent-prompt~ refuses only when the pane's state is already =:blocked=
(src/mux/server.lisp:451-464). When finding 1 has made that state
unreachable, nothing refuses.

Demonstrated on a benign pending command. test:1 was sitting on a bash
permission dialog for ~python3.13 -m pytest tests/ -q~, and atty reported it
=idle=:

: state before: test:1  agent  idle
: $ atty agent prompt test:1 'STATUS?'
: prompt exit: 0

The paste plus the automatic Return confirmed the highlighted option and
*ran the command*. The next read showed test results.

So the composition is: a pane is mis-classified (1), which makes its state
wrong, which turns an ordinary prompt into consent on a dialog the caller
never saw. An orchestrator polling ~agent list~ and prompting whatever says
=idle= will approve dialogs on its own. Fixing 1 removes the exposure here,
but the guard is worth hardening anyway.

** 4. =agent read= cannot tell Claude Code's suggestion from typed text

After a turn, the prompt box renders a greyed suggestion, and ~agent read~
shows it exactly as it shows real input:

: ❯ add clarification 8 with a TODO_FILE env var override

Sending ctrl-u left it untouched, which is how it was identified as a
suggestion rather than a draft. Cosmetic for state detection, since
~live-prompt-box~ matches on the ~❯~ either way, but a caller reading the
screen to decide what a pane is waiting for can be misled.

* What worked

- The macOS build. Four concurrent Claude Code TUIs plus the orchestrating
  pane, about twenty minutes, no crash, no redraw corruption, no wedged
  pty. The ~poll~ rewrite holds up under real load.
- Session lifecycle. ~atty serve~ backgrounded, ~atty list~, sockets under
  /tmp/atty-501/, all clean. Sessions were still healthy at the end.
- ~agent read~. Exact screen text every time, including box drawing and the
  two column layout. This carried the whole run.
- ~agent say~. ~\e[B~, ~\r~, and bare digits all landed correctly in dialogs.
  Every dialog in the run was answered this way.
- ~agent explain~. The ranked rule table with the matched rule and the text
  it matched is genuinely good, and it is what identified finding 1: the
  empty table on the worker panes was the tell.
- ~agent trace~ gave per look ms / moved / said / state rows.

* Reproducing

The control is the cheapest part to keep. Start one session with
~claude ...~ as the whole command and one with ~cd dir && exec claude ...~,
put both on a permission dialog, and ~atty agent list~ them. They should not
disagree.
