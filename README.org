#+TITLE: cl-vt

A terminal emulator in Common Lisp. It reads what a program wrote and keeps the
screen that means: a grid of cells, each with the face it was written in, a
cursor, a scroll region, an alternate screen and a scrollback. It draws nothing
itself. What you do with the grid -- paint it, put it in a buffer, diff it
against the last frame -- is yours.

* The shape of it

A terminal is a struct. You make one, you tell it what a program said, and you
read the screen back:

#+begin_src lisp
  (let ((term (vt:make-term :width 80 :height 24)))
    (vt:term-process-output term (format nil "~C[1;32mhello~C[0m" #\Escape #\Escape))
    (vt:term-dump-row-string term 0))          ; => "hello ..."
#+end_src

Output arrives in whatever pieces it arrives in. A sequence split across two
reads is still one sequence: the parser keeps its state on the term, so feeding
it a byte at a time and feeding it a megabyte give the same screen.

A cell is a character and a face. A face is shared: every cell written under the
same SGR points at one =face-attrs=, so a screen of coloured text is a screen of
pointers and a diff can compare with =eq=.

#+begin_src lisp
  (vt:cell-char (aref (vt:term-grid-row term 0) 0))   ; => #\h
  (vt:face-fg (vt:cell-face (aref (vt:term-grid-row term 0) 0)))  ; => 2
#+end_src

A colour is an index into the 256-colour palette, or a =(r g b)= list when the
program asked for one. =color-index-to-rgb= answers what an index is worth.

** Reading a line

Three ways, depending on who is looking:

#+begin_src lisp
  (vt:term-render-line term 0)      ; => "hello ...", ((0 (:fg 2 :bold t)) (5 nil))
  (vt:term-render-ansi-line term 0) ; => the line with its escapes put back
  (vt:term-dump-row-string term 0)  ; => just the characters
#+end_src

=term-render-line= is the one a drawing loop wants: the characters, and a list of
the columns where the face turns, as a plist each. =term-render-ansi-line= writes
the line back out as a program would have written it, which is what you print at
a real terminal and what a round trip is tested against.

** What it answers

A program asks a terminal questions -- where is the cursor, what are you, what
colour is your background -- and expects an answer on its input. Give the term an
=input-fn= and it answers them:

#+begin_src lisp
  (vt:make-term :input-fn (lambda (term said) (pty:pty-write-string fd said))
                :title-fn (lambda (term title) (setf (window-name) title))
                :bell-fn  (lambda (term) (flash))
                :cwd-fn   (lambda (term cwd) (remember cwd)))
#+end_src

** Typing at it

The other direction is =key-event-to-escape-sequence=: a character, or a key and
its modifiers, into the bytes the program reads. It knows which mode the keypad
is in, because the program said.

#+begin_src lisp
  (vt:key-event-to-escape-sequence term #\a)             ; => "a"
  (vt:key-event-to-escape-sequence term '(:up))          ; => ESC [ A
  (vt:key-event-to-escape-sequence term '(:up :ctrl))    ; => ESC [ 1 ; 5 A
  (vt:key-event-to-escape-sequence term '(:f5))          ; => ESC [ 1 5 ~
#+end_src

* A program to read

=vt/pty= is the other half: a program on a pseudo-terminal of its own, with a
session and a controlling terminal, so that ^C is a signal and a resize is a
SIGWINCH rather than a byte nobody reads.

#+begin_src lisp
  (multiple-value-bind (fd pid) (pty:spawn-pty-process "htop" :rows 24 :cols 80)
    (loop :while (pty:pty-wait fd 100)
          :for said := (pty:pty-read-string fd 8192)
          :while said
          :do (vt:term-process-output term said))
    (pty:pty-close fd)
    (pty:pty-reap pid))
#+end_src

There is no C here and nothing to compile. The pty is =posix_openpt=, the spawn
is =posix_spawn=, and both are in libc, which is already under every sbcl there
is; =sb-alien= calls them and =sb-unix= does the reading, writing, polling and
ioctl.

fork is not an option and not merely a risk: =sb-posix:fork= refuses outright in
an image with threads, and any real application has threads. posix_spawn is the
only door -- but posix_spawn has no hook to run code in the child, which is the
one thing a controlling terminal traditionally needs, and is why this used to
ship a helper program written in C. It does not need one. =POSIX_SPAWN_SETSID=
makes the child a session leader with no terminal, and then the child *opens the
slave by name* instead of inheriting it already open, because opening a terminal
is how a session leader with none takes one. That is the whole difference between
=addopen= and =adddup2=, and it is what removed the C.

=pty-wait= is why there is a poll and not a blocking read: a blocking read cannot
be interrupted. Closing the descriptor under it does not wake it, and killing the
thread inside a foreign call wedges the image at the next GC. So a reader waits
with a timeout and looks at its own flag between waits.

The two systems are separate. =vt= is portable Common Lisp with no dependencies
at all, and is what you load if the bytes come from somewhere else -- a socket, a
file, a log. =vt/pty= is the sbcl-shaped half.

** What a system calls a thing

Four numbers differ between systems, and they are all at the top of
=src/pty/pty.lisp=: =O_RDWR=, =O_NOCTTY=, =POSIX_SPAWN_SETSID= and =TIOCSWINSZ=.
Every one of them is frozen ABI -- TIOCSWINSZ has not moved since the 1980s -- so
the table is written once and does not rot. The BSD ioctl numbers are not
tabulated but derived, because a BSD ioctl number is a documented bit layout
rather than a list, so one rule covers macos and every BSD. A system nobody has
checked stops at load saying which number it wants, rather than running and
handing back a pipe that answers isatty.

Nothing here defines a struct that differs between systems. =struct winsize= is
four unsigned shorts everywhere, which is why it is safe to write down;
=posix_spawn_file_actions_t= and =posix_spawnattr_t= are opaque, so they get
more room than any system needs and their own init call fills them. =termios= is
the one that really differs, and nothing here touches it: a master does not need
it and a shell sets what it wants on the slave.

Which is to say the answer to "is it right on this system" is not a header, it
is the pty suite. Four of its tests assert what a terminal is and a pipe is not:
that the child leads its own session on this pty, that it can open =/dev/tty=,
that a resize arrives as a signal and =stty size= agrees, and that an interrupt
character becomes SIGINT. Get =POSIX_SPAWN_SETSID= wrong for a system and all
four fail at once, loudly, in two seconds.

* What it knows

Cursor movement and addressing, save and restore. Erase in line, in display, in
character. Insert and delete characters and lines. Scroll regions, index and
reverse index. Auto-margin and insert mode. The alternate screen, and a
scrollback that the alternate screen does not write to. Tab stops every eight
columns, forward and back. Titles and working directory through OSC 0, 2 and 7,
and the colour queries. Device attributes and device status. Cursor shape, both
ways it is asked for. Bracketed paste. The DEC line drawing charset in all four
slots, with shift out and shift in. Wide characters, which take two columns and
will not be split across the margin, and combining marks, which take none.

SGR: bold, faint, italic, underline, blink, inverse, conceal, crossed out; the
eight colours, the bright eight, the 256, and true colour; underline colour and
underline style, said with semicolons or with colons.

DCS is parsed far enough to be skipped.

* Building it

Nothing is built. There is no C, so there is no compile step, no shared library
and no helper program -- =(asdf:load-system :vt/all)= is the whole of it.

Two ways to get an sbcl and the test systems, and every target works under
either. Guix is what it develops against and what plain =make= uses; =FOREIGN=1=
is for a machine without it, where the lisp systems come from wherever asdf
already finds them.

#+begin_src sh
  make test              # the fiveam suite
  make check             # load everything and say so
  make repl
  make run CMD='top -b -n 1'    # a command on a pty, and the screen it drew
  make mux               # a shell in a session of its own, in this terminal
  make bench             # bytes a second
  make latency           # what one read costs, and what a terminal weighs
  make mux-bench         # what a frame costs, and what a keystroke costs
  make compare           # the same corpora through tmux and alacritty
  make FOREIGN=1 test
#+end_src

* How fast

=make bench= reads 32 MB corpora -- plain text, coloured text, and full-screen
redraws -- through the parser and again through a real pty, and =make compare=
puts the same bytes through tmux and through an alacritty in a headless sway of
its own, so the three numbers are read off one screen. On a Ryzen AI Max+ 395,
80x24, through a pty:

|        | cl-vt    | tmux, detached | alacritty |
|--------+----------+----------------+-----------|
| plain  | 79 MB/s  | 74 MB/s        | 107 MB/s  |
| colour | 62 MB/s  | 43 MB/s        | 128 MB/s  |
| redraw | 88 MB/s  | 44 MB/s        | 29 MB/s   |

tmux detached is the fair comparison: no client is attached, so it is parsing
and keeping a grid and drawing nothing, which is all cl-vt does. alacritty is
drawing as well, in software, which is what its redraw column costs it.

Nothing in here is written for speed -- no unsafe declarations, no unrolling,
no special-cased fast paths. What the numbers took was telling the compiler what
it was already holding: a row is a =simple-vector=, output is a
=(simple-array character (*))=, and a colour is nearly always a number, so it is
compared with =eql= before anything asks =equal=. Before that it read 40 MB/s.

=make run= is the short demonstration: it puts a command on a pty, reads until it
stops talking, and prints the screen back with its escapes.

* Many terminals inside one

=vt/mux= is a multiplexer built on the emulator, running inside the terminal you
are already in. =make mux= puts a shell in a session of its own; =C-b d= detaches,
=C-b r= redraws, =C-b C-b= types a =C-b=. =make mux MUX=list= says what is
running, and =make mux MUX=<name>= joins a session by name, starting it if it is
not there.

It is a server and a client from the first line. The server holds the sessions
and never goes near a terminal; a client attaches over a unix socket in
=$XDG_RUNTIME_DIR/cl-vt/= and owns the one it is sitting in. Detaching leaves the
programs running, and a client that comes back is simply one whose whole screen
is out of date.

** What goes over the socket

Cells, never escape sequences. The server composes the panes into a host-sized
grid, diffs it against a shadow of what each client was last sent, and puts the
runs that moved on the wire as characters and faces. The client turns those into
escapes for its own terminal. That is the whole reason the split is where it is:
only the client knows what the terminal in front of it can show, so a session
whose escapes were settled by whoever attached first could not be picked up from
a different terminal.

A message is a byte count, a newline, and one s-expression in utf-8. The count is
there because the loop may not block: a form read straight off the descriptor
would stall every pane in the server on one message that arrived in two pieces.
=*read-eval*= is nil, so a =#.= in a payload signals rather than runs.

Typed bytes go through untouched. The client watches for one prefix byte and
forwards everything else exactly as the terminal sent it -- mouse reports,
pasted text, whatever encoding it was built with. Decoding keys and encoding them
again would narrow all of that to the intersection of two tables.

The emulator will still read bytes back into keys when something wants them
named -- =vt:escape-sequence-to-key-event= is the inverse of
=vt:key-event-to-escape-sequence=, and the suite holds the two of them to it over
every key and modifier the old encoding has room for. It answers how many
characters it took, and nothing at all when what is there is the beginning of
something longer.

** What a frame costs

The question the whole design turns on: composing, diffing and encoding a frame
has to fit inside the 16,666 us a terminal showing sixty frames a second has.
=make mux-bench= says it does, by a factor of six hundred.

|        | blit | diff | encode | whole frame, p99 |
|--------+------+------+--------+------------------|
| 80x24  |  2.4 |  3.6 |   11.7 |             26.9 |
| 300x80 | 29.2 | 31.3 |   39.2 |            171.0 |

Microseconds, over the coloured-text corpus. The diff is cheap for a reason the
emulator already had: faces are shared, so comparing two cells is one =char== and
one pointer compare. A run reaching the end of a row that is blank the rest of
the way is an erase rather than a row of spaces, which is most of the win on
redrawing output.

** What a keystroke costs

The number a person actually feels, measured end to end: a byte written at the
client, through the socket, the server, the pane's pty, the program, the parser,
compose, diff, encode, and back out as the escapes that show it.

| least gap between frames | p50 us | p99 us |
|--------------------------+--------+--------|
|                     0 ms | 342.7  |  521.6 |
|                     4 ms | 291.9  |  608.2 |
|                     8 ms | 282.2  |  469.8 |
|                    16 ms | 13332  |  13575 |
|                    33 ms | 12527  |  13656 |

That gap is a least gap, never a tick: a client that has heard nothing recently
is answered the moment a byte arrives. The last two rows are what happens when
it is set wide enough to bite -- typing faster than the gap, every keystroke
waits out the rest of it. Eight milliseconds is the default because it is the
widest that never showed up in the number.

The socket carries between 1.3 and 2.0 times what the terminal reads -- 1076
bytes a frame against 642 on the redraw corpus. S-expressions are not what this
costs, so the wire stays readable: =socat= on it shows you plain text.
